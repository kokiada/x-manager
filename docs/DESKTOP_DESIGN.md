# デスクトップアプリ設計（本家 XBoard 方式）

2026-11-22、こうきくんの指示で開始。体制：ゆい＝PM＋設計、ボブ＝技術リーダー、ガッツ＝開発メンバー。

## 1. 目的

現行の Chrome 拡張方式の限界を超えるため、実行基盤をデスクトップアプリ（Electron）に移す。

拡張方式の限界（2026-11-22 時点で判明しているもの）：

- IP が全アカウント共通になる。Chrome のプロキシ設定はプロファイル単位でしか変えられず、アカウントごとに分けられない。
- セッションはブラウザ全体の Cookie をジョブごとに差し替える方式で、実行中は x.com タブと干渉する。
- Service Worker の癖（再読み込みしないと新コードが効かない、生成器の fetch が実ブラウザ固有の挙動で失敗する等）に運用が左右される。

デスクトップ方式で得るもの：

- アカウントごとに独立したブラウザセッション＋個別プロキシ（本家 XBoard と同じ構造）。IP をアカウント／プロキシグループ単位で分けられる。
- Cookie の差し替えが不要になる（セッションが最初から分離）。
- 実行環境をアプリが管理するため、拡張の再読み込み等の手作業が消える。

## 2. 全体構成

```
┌─────────────────────────────────────────────┐
│ Electron ホスト（メインプロセス）             │
│  ・アプリ画面の配信（既存 dist を同梱）        │
│  ・セッション実行部                            │
│    - アカウントごとの session partition       │
│    - partition ごとの proxy / cookies         │
│    - 非表示 WebContents 上で x.com を開き、    │
│      ページ文脈の fetch で内部 API を実行      │
│  ・トークン保管（ホスト内のみ）                │
└───────────────▲─────────────────────────────┘
                │ ブリッジ（IPC / contextBridge）
┌───────────────┴─────────────────────────────┐
│ 既存 Web アプリ（レンダラ）                   │
│  ・画面・業務ロジックは現行のまま              │
│  ・DesktopExecutor が Executor を実装し、     │
│    ジョブをホストへ渡す（拡張プロトコルと同形）│
└─────────────────────────────────────────────┘
```

- アプリ側の差し替え点は既存の `Executor` インターフェース。`executorMode` に `'desktop'` を追加する。拡張方式（`'extension'`）は当面存続させ、併用・切り戻しを可能にする。
- ジョブ／結果／セッション一覧のメッセージ形は `src/executor/protocol.ts` を土台に揃え、拡張方式とアプリ側コードを共通化する。

## 3. アカウントセッション

- アカウントごとに `session.fromPartition('persist:xmgr-<accountId>')` で分離する。Cookie・キャッシュ・ストレージは partition 単位で独立し、再起動後も保持される。
- 認証は partition の `session.cookies` に `auth_token` / `ct0` を設定する（Electron の正規 API。拡張を Electron で動かしたときの壁＝chrome.cookies 不在とは無関係）。
- プロキシは partition の `session.setProxy()` で設定する。単位はアプリ既存のプロキシグループ（1 グループ＝複数アカウント、本家の運用目安は 1 プロキシあたり約 5 アカウント）。プロキシ未設定のアカウントは直接接続。
- 取り込みは拡張方式と同じ発想：そのアカウントでログインした状態から Cookie を読む。デスクトップ方式では partition ごとにログイン用ウィンドウを開く形を基本とする（手入力・貼り付けに依存しない）。

## 4. 実行方式

- 実行は各 partition に属する非表示（または最小化）WebContents で x.com を開き、そのページ文脈で fetch する。ページ文脈で送るため、Referer やブラウザ指紋は通常の閲覧に近い形になる。
- 同時に開く WebContents 数は上限を設ける（既存設定「同時保持ブラウザ数」を流用。ただしメモリ配慮のため初期値は小さくし、ジョブのたびに開閉する方式も選べるようにする）。
- ジョブはアカウント内で直列化する。アカウントが違えば partition が別なので並行実行が可能（拡張方式の全体直列より速くなる）。
- x-client-transaction-id は生成器（transactionId.js）を流用する。ページ文脈には DOM があるため、移植時の置き換え（HTML 文字列解析）は本来の DOM 実装に戻す選択肢もある。Phase 0 でどちらが安定するか確認する。

## 5. 流用マップ（ガッツの棚卸しで詳細化）

- そのまま流用できる見込み：xClient のエンドポイント定義と GraphQL 呼び出し形、queryId 解決（動的スキャン＋フォールバック）、dispatch の各メソッドの処理、エラー分類と日本語文案、メディアアップロード（INIT/APPEND/FINALIZE）、コミュニティ投稿、メールチェック（タスク3の OAuth 方式）。
- 作り直し：セッション管理（Cookie 差し替え→ partition 分離）、transport（postMessage → Electron ブリッジ）、ポップアップ UI（取り込み→ホスト側のセッション管理画面）。
- 不要になる：declarativeNetRequest の Referer ルール（ページ文脈では自然な Referer になる）、clientIdentity の固定 ID（実ブラウザ文脈のため。Phase 0 で要否を確認）。

## 6. セキュリティ原則（拡張方式から継承）

- auth_token はホスト（利用者の PC）の中にだけ置く。レンダラ（アプリ画面）や外部に渡さない。
- ジョブ結果・ログにトークンの値を含めない。
- プロキシの認証情報もホスト内にのみ置く。

## 7. フェーズ計画

- **Phase 0：技術検証（ボブ）** — partition 分離＋ setProxy ＋ cookies 設定＋ページ文脈 fetch で、1 アカウントの投稿が通ること。transaction-id の扱い（生成器流用か DOM 実装か）の確定。同時保持数のメモリ感の測定。
- **Phase 1：基盤（ゆい＋ボブ）** — Electron ホスト、ブリッジ、DesktopExecutor、セッション管理（取り込み・一覧・削除）。アカウントチェックと投稿だけ先行。
- **Phase 2：全機能移行（ガッツ＋全員）** — 残りメソッド（書き込み系・分析・通知/DM・メディア・コミュニティ・バンチェック・メール）の移行と、プロキシグループ連携。テストは現行ルールどおり 100% 成功が完了条件、PROGRESS.md に記録。
- **Phase 3：配布・運用** — Windows ビルド（インストーラ＋ポータブル）、バージョン表記のホスト対応、運用手順書（プロキシ調達・割り当ての目安を含む）。

## 8. リスクと未決事項

- Electron 同梱 Chromium で x.com が通常表示・動作するか（Phase 0 で確認）。
- プロキシの調達は利用者側（費用・運用は別途相談）。
- メモリ使用量：アカウント数が多い場合の同時保持数の設計。
- 配布物の署名なし警告への案内（前回の exe 配布と同じ論点）。
- スマホからの利用は「閲覧・指示」まで。実行は PC のホストが担う（本家と同じ制約）。
