# x-manager 設計方針（XBoardクローン）

調査の全文は [xboard-research.md](./xboard-research.md) を参照。本書はクローンの設計判断をまとめる。

## 1. プロダクト概要

- XBoard（x-board.net）のクローン。X（旧Twitter）の複数アカウントを一元管理するWebアプリ。
- 品質目標：売り物にできるレベル。
- PC・スマホ両対応（レスポンシブ＋PWA）。本家はPC専用デスクトップアプリだが、本プロジェクトはブラウザで動くことが要件。

## 2. 本家のコア原理（調査結果）

- X APIを使わない。アカウントごとに分離したブラウザセッションで直接Xにログインし、全操作をブラウザ経由で行う。
- アカウントごとに個別プロキシ設定、auth_tokenによるトークンログイン、ログイン情報は端末内にのみ保存。
- 主要機能：一括投稿（テンプレート/ランダム文言/ツリー/予約/自動投稿）、一括いいね・リポスト・ブックマーク＋自動操作、サーチバンチェック、アカウントチェック（状態＋通知/DM件数＋フォロワー数）、ポスト分析・追跡・フォロワー推移、CSV管理、端末同期、リモート操作。

## 3. 実現可能性とアーキテクチャ判断（重要）

ブラウザ上のWebアプリだけでは、本家のコアである「x.comへのauth_token Cookie注入」「アカウント別プロキシ経由の実ブラウザ操作」はブラウザのセキュリティモデル上そのまま再現できない。そこで実行層を分離する：

- **管理コンソール（Webアプリ本体）**：アカウント台帳、グループ、プロキシ割当、状態管理、一括操作のキューとロジック（順序・間隔・テンプレート展開・ツリー生成・予約）、バンチェック手順、分析、CSV入出力、同期。本家の仕様数値（間隔1〜60秒、テンプレート2,000件、ランダム文言[Random1]〜[Random2000]、メディア上限など）を忠実に実装する。
- **Executor（実行層インターフェース）**：操作を実際にXへ届ける層を差し替え可能にする。初期出荷はシミュレータExecutor（デモデータで全フローが動く）。将来、ローカルエージェント／ブラウザ拡張／デスクトップラッパーが同じインターフェースで実操作を担当できる。
- **データは端末内保存**（IndexedDB）を基本とし、本家の「サーバーに送信しない」思想を踏襲。端末同期は暗号化エクスポート/インポートとして設計する。

この分離により、UIとロジックは本家同等レベルまで作り込め、実操作の接続は後から差し替えられる。

## 4. 技術スタック（案）

- Vite + React + TypeScript（SPA、PWA対応）
- 状態管理：軽量に（React Context + hooks、必要に応じZustand）
- データ：IndexedDB（Dexie）
- スタイル：CSS変数によるデザイントークン＋モバイルファーストのレスポンシブ
- テスト：Vitest（ロジック層中心）

## 5. 画面構成（案）

1. ダッシュボード（アカウント状態サマリ、要対応アラート）
2. アカウント一覧（グループ絞り込み、状態バッジ、プロキシ表示、チェック実行）
3. アカウント詳細（セッション/プロキシ/auth_token管理、個別指標）
4. 一括投稿（テンプレート、ランダム文言、ツリー、予約、メディア）
5. 一括操作（いいね/リポスト/ブックマーク、自動操作ルール）
6. バンチェック（サーチバン実行・結果一覧、定期チェック）
7. 分析（ポスト分析、ポスト追跡、フォロワー推移）
8. 通知/DM集約
9. データ管理（CSV入出力、バックアップ/同期）
10. 設定（プラン、同時保持数、定期チェック）

## 6. タスク分担（案）

- **ゆい（プレイングマネージャー）**：全体設計・デザインシステム、アプリシェル/ナビゲーション、アカウント管理（台帳・グループ・プロキシ・CSV）、一括投稿エンジンと画面、統合・レビュー・品質管理
- **ガッツ**：アカウントチェック＆サーチバンチェックのワークフローと判定ロジック、分析（ポスト分析・追跡・フォロワー推移）、自動投稿・自動操作エンジン、通知/DM集約

## 8. 統合メモ（2026-11-21、ガッツのブランチ `gatts/check-analytics-automation`）

ガッツのブランチ（`1468426`、ベース `604887e`）は本線（`233e7f4`、全10セクション動作済み）に後から到着したため、ブランチ全体のマージではなく、内容を比較して良い部分だけ本線へ取り込んだ。両実装は同じ設計書から生まれたためデータモデルは似ていたが、本線は DB v4（11テーブル）、ガッツ側は DB v4相当（6テーブル）と別系統のため、UI/ロジックは本線のスキーマの上に移植した。ガッツのブランチは origin に残したまま（削除しない）。

- **バンチェック（06）**：本線を採用（リプライバン注記・24時間以内判定の投稿連動・定期チェック配線が揃っているため）。ガッツの `searchBanVerdict`（話題×最新の判定を SearchBanState に写す純粋関数）は `banCheckService.ts` に移植し、画面の判定ラベル生成に使った。テストも移植。
- **一括操作（05）**：本線の画面・サービスを採用（ランダム選出枠・キュー順・履歴が揃っているため）。ガッツの実装にあった **一括フォロー**（§8）を移植：`BulkActionKind` に `follow` を追加し、フォロー対象は @handle、実行は Executor の `executeAction`（follow はシミュレータ済み）経由。`authorHandleFromUrl` は twitter.com リンクにも対応させた。
- **分析（07）**：ガッツの `analytics.ts` から `seededRandom` / `simulateMetrics` / `engagementRate` / `viewsPerHour` / `trackedPostsFromJobs` / `followerTrend` を本線の型（`PostAnalytics` / `FollowerHistory` / `PostJob`）に合わせて移植。ソートキーに `engagement` を追加し、ポスト追跡のスナップショット補完とフォロワー推移チャートの欠測区間判定に使った。テストも移植。
- **自動投稿・自動操作**：ガッツの `automation.ts` は本線の `autoPost.ts` / `autoAction.ts` と機能が重複するため全体移植はせず、**決定論的スロット**の考えだけ取り入れた：`autoPostEngine` がルール＋日付をシードにした乱数でスロットを計算し、ティックごとに時刻が動く問題を解消した。`autoActionMatches` / `autoActionReactors` / `dailyCapReached` は本線の同等関数（`matchesKeywords` / `eligibleActingAccounts` / `dailyCapReached`）で既にカバー済み。
- **チェック系サービス・通知**：ガッツの `checkService.ts`（CheckRun モデル）と `inboxItemsForCheck` は、本線の `banCheckService.ts`＋`notificationService.ts`（Executor 経由の取得・永続化）で既に同等以上に実現済みのため不採用。`AutomationRuleForm` の統合ルールモデルも、本線の自動投稿ルール／自動操作ルールを分けた設計を維持するため不採用。
- **バックアップ**：ガッツの `backup.ts` は彼の6テーブル分で、本線のバックアップは既に v4 全11テーブルを対象済みのため不採用。
